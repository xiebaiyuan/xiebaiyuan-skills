# 新模型/新产品发布深度调研

## When to Use（何时用）

有人转发一条「XX 发布了新模型」的消息，或者甩一个搜索链接说「从这里开始调研」。
产物是一份能直接分发的深度文档，不是一份链接摘要。

和相邻技能的分工：

| 技能 | 干什么 | 区别 |
|:--|:--|:--|
| `trendshift-deep-research` | 每日扫榜，批量建档 | 广度优先，单项目浅 |
| `release-boundary-forensics` | 判断一次发布到底交付了什么 | 只做边界判定，不写可分发文章 |
| **本技能** | 单个新发布物做深度、可分发、带理论底的长文 | 深度优先，一篇吃透 |

## 第一步：先确认它到底是什么（不要跳过）

用户给的搜索词可能是缩写、谐音、或者多义词。**先把指代确认下来再动手**，否则会写一整篇错的东西。

做法：抓一次搜索页 + 一次带上下文的关键词搜索，然后用一句话向用户复述「你要的是不是这个」，再继续。

（实例：`Jev模型` 一开始可能是经济学概念，实际指向的是 TypeSafe AI 刚发布的推理模型。一句话确认省掉整篇返工。）

## 核心方法：六层信息源

按这个顺序取，每层都有它不可替代的作用。**缺哪层，文章就在哪层露怯。**

### 第 1 层｜官方一手（必取）

优先级：发布博客 > 产品文档 > 宣言/manifesto > FAQ。

要从这一层挖四样东西：

1. **命名来处**。FAQ 里通常直接回答。别自己猜词源——猜错了整篇的理论框架就错了。
2. **规格与定价的精确值**，不是概数。
3. **官方自己承认的失败模式**。很多产品文档有专门的「已知限制」页，这是全文最有价值的一节。
4. **官方基准的自我披露**。找「参考答案怎么来的」「为什么某些模型不在对比里」这类句子。

### 第 2 层｜官方基准的口径

官方给的「快 N 倍、便宜 M 倍」必须连同分母一起记下来。**没有分母的倍数不是数据。**

### 第 3 层｜第三方独立实测（可信度最高的一层）

找有没有机构拿自己的数据做过对照。这是全文唯一能拿到「绝对数字」的地方。

取的时候注意三件事：

- **测的是「一致率」还是「准确率」？** 一致率不等于正确率，两个模型犯同样的错也会一致。作者自己通常会在注释里说明，务必引用这句限定。
- **成本列的分母是谁？** 同一张表里不同基线的成本可能差两个数量级。
- **样本量和方法论**要写进文档，读者才能判断。

### 第 4 层｜社区批评

Hacker News / 相关论坛的发布贴。**目标是找到最强的反对意见，不是找共鸣。**

挑评论的标准：

- 指出「宣传口径与实测口径不一致」的
- 指出「厂商最得意的那个指标其实在测别的东西」的
- 提出「那为什么不用更简单的既有方案」的
- 厂商自己下场回应了的（回应本身也是信息）

### 第 5 层｜学术理论基线（这是「理论深度」的来源）

**新概念背后一定有既有文献。** 找出它、讲透它，文章的分量就出来了。

做法：把产品或方法的名字拆开，对每个术语做一次学术检索。

| 产品声称 | 该去查的既有文献 |
|:--|:--|
| 名字取自某个历史人物/现象 | 那个现象的一手著作 + 后续学术争论 |
| 提到某个训练方法 | 该方法的同类论文（proper scoring rule / 校准 / RL 目标函数） |
| 提到某种认知科学类比 | 原理论的完整表述，包括它被借错的地方 |

引用学术文献要**引原话**，并注明「证据远非定论」这类限定——好的论文自己会写，照抄比转述安全。

### 第 6 层｜真实部署案例

找已经在跑的项目，优先要**可核实的数字**（成本、耗时、条数）。

归档数字时要标清来源性质：开发者自述 ≠ 受控实验。两者量级能对上就可以用，但要在文档里写明。

## 访谈/人物类调研：靠三角互证找修正

调研对象是**一个人和他的方法论**（一期播客对谈、一场演讲、一套技能仓库）时，方法要换。这类的价值不在「转述讲了什么」——用户手里的转述往往已经很完整——而在**核实**。

三个取证面必须都打：

| 面 | 取什么 | 为什么不可替代 |
|:--|:--|:--|
| **本人开源产物** | 他自己的仓库、文档站、词典、README、skill 文件 | 是他**写下来**的定论，比口头表述精确，且常带口头没说的限定语 |
| **本机已装的那套东西** | 若对象的方法论已经被装进本机（skills 目录、插件、CLI），直接读源文件 | 访谈说的是「我怎么用」，源文件是「实际怎么写的」，两者会差；而且能验版本漂移 |
| **第三方独立印证** | 别人复述该概念时标注的出处、竞品仓库、论坛讨论 | 归属关系（这概念到底是谁的）只能靠这一面定 |

**最大的收获几乎总是「归属纠错」。** 广为流传的说法常把某个概念安到最有名的那个人头上，而他在访谈里会亲口说「这是某某的想法，对我影响很大」。**访谈原文里的归功句是必搜项**：搜 `influence`、`got it from`、`borrowed`、`originally`。找到后用第三方材料反查一次，确认不是客套。

同样必搜的还有**限定语**。作者本人写的文档里那句 `though this is debated`、`据我所知`、`早期数据`，在转述中几乎必丢。把限定语找回来单独成段，这本身就是文档的增量。

**数字要在同一人身上对齐**：同一个人在不同场合给的同一个数字可能不同（访谈里一个值、正式文档里一个区间、社媒上又一个）。三个都列出来对照，比只引一个更有信息量——漂移本身就是「这个数字有多可靠」的证据。

**时间差要查**：播客/文章的选题周期通常几个月，而对象的方法论可能已经换过一轮。查「访谈发布时，他还在用当时推荐的那个工具吗」——这一条经常能挖出「他说的是招牌技能，其实自己早换了」这类观察。

## 公众号文章核查：核查类调研的交付物是「文章漏了什么」

用户的请求是「深度调研 <某篇文章链接>」时，真正的价值不在转述文章，而在两件事：**逐字核它引的数字**，和**找它删掉了什么**。

接手后按这个顺序做：

1. **抓原文**。微信公众号（`mp.weixin.qq.com/s/...`）用手机版 UA 直接 curl 能拿到，正文在 `<div id="js_content">` 里；发布时间从 `var ct = "<unix>"` 取。
2. **建三列表**：`文章的说法 ｜ 一手源实际值 ｜ 核对结果`。能把每一项标成 ✓ / 偏保守 / 过期 / 错，比笼统说“准确”有力得多。注意**区分“错”和“过期”**——文章是快照，源在持续变，这两件事性质不同。
3. **找遗漏**。去原始仓库/原文把文章引的那一条**全文读一遍**（尤其备注/局限/禁忌段），和文章的转述**逐字对比**。推荐类文章的结构性毛病就是删掉限定条件与反方证据，只留收益——这是全文最实在的一条发现。量化的对照表达（“源的备注栏 168 字，文章对应位置 0 字”）比形容词可信。
4. **核到一手文献，不是二手汇总**。医学数字回 NEJM/PubMed 原文（DOI 直查），法条回国家法律法规数据库。核不了的在信源表里标 `[待验证]`，不要因为多家二手都说一样就当核过了。
5. **补文章没覆盖的层面**：作者身份与可信度、社区 issue 里作者怎么处理质疑、同类项目与衍生生态、变现/利益关系。

**刷荐号不要先入为主当“水号”。** 先查它的主体身份（公众号名前缀不一定等于 GitHub 组织名，用主仓库的 star 数判体量）；它们通常没写错数字，错的是选择性。

## 借用厂商订阅的插件：先查条款，再数 case

调研对象是「把某家厂商的订阅额度接进第三方 harness」这类工具（包装官方 CLI、掏 OAuth token 打私有 API、多账号池轮换）时，交付物的核心是一句话：**这样用会不会把号弄废。** 三层证据按顺序打，不要靠推测。

**第一层：厂商服务条款原文。** 这类风险几乎总被条款直接点名，措辞比想象中具体。`curl` 抓条款页正文再去标签，搜 `third party`、`third-party software`、`suspend`、`termination`、`violation`。抓到的往往是逐字可引的判决句（实例：Antigravity 条款写明「用第三方软件、工具或服务访问本服务，举例是 OpenClaw 配 Antigravity OAuth，构成对本协议的违约，可能成为暂停或终止账号的理由」）。注意处罚范围那句的后半截，通常不是只停一个产品。

**第二层：厂商有没有发过执法公告。** 条款是常设的，公告才说明「什么时候开始真下手」。去官方仓库的 discussions / announcements 搜 `abuse detection`、`policy-violating`、`rate limit`。拿到公告日期后**和封号 issue 的提交日对齐**，两者同日基本不是巧合。

**第三层：case 挖掘。** `gh search issues` 横扫生态（代理类、轮换类、CLI 包装类都要扫），关键词至少三组：英文 `banned`/`suspended`/`revoked`、中文 `封号`/`封禁`/`风控`、报错码 `403`/`PERMISSION_DENIED`。挑出封号 issue 后逐个取 `created_at` 排时间线，**同日聚集的那天就是厂商的一次集体动作**，比任何单条案例都有说服力。

**分类是一切起点：先按「请求怎么到达厂商」把工具分族。**

| 族 | 做法 | README 特征 |
|:--|:--|:--|
| 桥接族 | 起官方二进制的子进程，解析它的结构化输出 | 免责声明通常只有一句「需遵守服务条款」 |
| 掏 token 族 | 用产品内置 OAuth 客户端换 token，直打私有 API | 常见「可能违反 ToS、账号可能被封」「指纹」「签名绕过」等自述 |

分完族再数 case，否则会把桥接族的低曝光误读成安全。判据是「条款定义里的处罚范围」，不是「网络上出现了什么指纹」——条款管的是「谁在驱动这个服务」，桥接族仍是第三方产品在驱动。另外要专门查一件反直觉的事：**标榜「只调官方 CLI」的项目是不是另外还直连了厂商接口**（常见的是自己轮询配额接口），这会把结论从「纯桥接」拉回灰色。

**几条必然遇到的取证困难，提前写进文档，别假装没有：**

- 封号案例几乎全是发帖人自述，没有分母也没有受控对照；被罚的来发帖、没被罚的不来，issue 数不能换算成封号率。
- 「我用了 N 周没事」不构成安全性证据。这类工具的失效方式是「先好用，后突然不能用」，只证明「还没被抽到」。
- 小生态的零案例可能是假阴性：先量双方用户基数（npm 月下载、star），差一个量级就不能把「没案例」当结论。
- 「厂商能不能识别」是黑箱且会变。只给「已证明会被判定」的清单，给不出「做什么一定安全」的清单。

**结论要落到「你动了什么」而不是「你装了哪个」**，按暴露面分档：只用官方客户端 / 桥接但单账号不碰池化 / 桥接 + 多账号轮换 / 掏 token + 指纹。同一条款对四档的适用是同一句，但触发概率与连带损失不同。

写作上有两处必须出现：一是**官方客户端正常、包装链路被封**的成对对照（用户原话常常就是「直接使用官方 APP 是没有问题的，由此确认被定向识别」），这是全文最有说服力的一句；二是**维护者自己的表态**，包括「我们也没办法」和「单账号用户建议直接用官方客户端」，后者往往是给提问者最直接的回答。

## 铁律：数字必须分口径列

这是这份方法里最容易出错、也最影响可信度的一环。

**同一个产品可以有互相矛盾的倍数，而且全都对。** 差别只在分母。

做法：文档里永远把数字分三栏（或三节）——官方口径 / 第三方实测 / 社区自述，然后单独用一段解释「为什么它们不一样」。

（实例：官方说「便宜 400 倍」；第三方对最贵的前沿模型实测 206 倍；对某个便宜的国产 flash 级模型只有 1.6 倍。三个数都成立。指出这一点，文章的可信度直接上一档。）

另外三类要专门警惕的数字：

- **厂商图上的 `0%`／`100%`**：先查它测的是什么。常见情况是「格式合规率」被当成「正确率」传播。
- **基准的 ground truth 是模型生成的**：存在继承性误差，答对也可能被记为错。
- **只在厂商自己页面上出现的绝对准确率**：标注方法未披露。

## 抓取技法与踩坑

**文档站先找 `llms.txt`。** 越来越多的产品文档站提供 `https://<docs-site>/llms.txt`，是一份给 agent 用的全站页面索引。拿到它能一次性摸清所有页面，很多 `.md` 版本可以直接 curl 下来，比解析 HTML 干净得多。

```bash
curl -sL --compressed -A "$UA" "https://docs.example.com/llms.txt"
```

**`web_extract` 会被拦。** 遇到 `Blocked: private or internal network address` 或中文站点直接失败，改用 curl 带 UA 取原文，再用 Python 去标签：

```python
import re, html
t = open('page.html', encoding='utf-8', errors='replace').read()
t = re.sub(r'<(script|style|nav|footer)[^>]*>.*?</\1>', '', t, flags=re.S|re.I)
t = re.sub(r'<[^>]+>', ' ', t)
t = html.unescape(t)
t = re.sub(r'[ \t]+', ' ', t)
t = re.sub(r'\n\s*\n+', '\n', t).strip()
```

走代理绕反爬可用 `https://r.jina.ai/<URL>`。

**优先抓仓库原始 `.md`，不要抓渲染后的页面。** 文档站的 HTML 里混着导航、订阅框、脚注，去标签后仍要人工挑。若内容在开源仓库里（文档站常见做法：正文存 GitHub，站点只是渲染层），直接拿 raw：

```bash
# 先列目录，确认文件名的真实写法（含空格、大小写）
curl -s -A "$UA" "https://api.github.com/repos/<owner>/<repo>/contents/<dir>" \
  | python3 -c "import sys,json;[print(' -',f['name']) for f in json.load(sys.stdin)]"
# 再逐个取原文（文件名要做 URL 编码）
curl -sL -A "$UA" "https://raw.githubusercontent.com/<owner>/<repo>/main/<dir>/<UrlEncoded%20Name>.md"
```

这一步还有个附带收益：**目录清单本身就是一份完整性证据**。数一下文件总数（如「71 个词条」）写进文档，比说「我读了一些」可信得多；也能顺带验证某个词**不在**里面（「XX 未收录」是个有效发现）。

**字幕抓取：`yt-dlp` 会撞 429，`en` 挂了就换 `en-orig`。** 两个语言分别请求，一个成功能拿到全文：

```bash
yt-dlp --skip-download --write-auto-subs --write-subs \
  --sub-langs "en-orig,en" --sub-format vtt -o "/tmp/<task>/yt.%(ext)s" "<URL>"
```

YouTube 自动字幕的 VTT **每一屏都是滚动重复的**（上一行会再出现一次带新时间戳）。必须按「文本内容」去重，否则段落数翻倍、grep 结果全是噪声：

```python
seen = set(); out = []
for txt in segment_texts:          # 已按时间戳切好
    if txt and txt not in seen:
        seen.add(txt); out.append(txt)
```

**自动字幕的专名错得离谱，要建纠错表。** 同一份字幕里常见：人名（`Tariq`→Thariq）、片名（`Momento`→Memento）、外来词（`lightvert`→Leitwort）、术语（`traceabits`→tracer bullets）、数值单位。做法是**逐条按上下文还原，还原不出来的不引用**——猜一个专名写进文档，比留白危险得多。纠错表本身作为工作文件留档，方便被人质疑时回查。

**大文档分段落盘，别一次 write_file。** 内容超过约 8K token 会流式超时。做法：每一节写一个独立文件到 `/tmp/<task>/doc_NN.md`，最后用 terminal 的 `cat` 拼成一个文件。这比「写头 + patch 续写」更稳，因为 patch 处理表格时 `\|` 会双重转义。

**中文字符串在 shell heredoc 里会被安全启发式拦。** 长命令、heredoc 都可能 exit 1。规则：脚本先 `write_file` 落盘，再 `bash` / `python3` 执行。

## 写作

- **先去 AI 味再交付**：只跑机械扫描不够。**通读全文**一遍再跑脚本，而且跑两轮——第一轮的命中里总有一批是「换个说法就合规」，第二轮专门收这些漏网。判定「保留」的命中必须说得出理由（引用块内的忠实翻译、合法的列表展开、自然否定句）。同时数口头禅频次：`顺带说`/`顺便`/`我觉得` 这类各超过 3 次就该稀释，重复口头禅比单个 AI 腔更刺眼。
- **结构**：章数按内容定，不要凑。开头一段「一分钟版本」+ 一段「口径提醒」，读者三十秒就能判断要不要读下去。
- **每个数字标口径**。引用原话时保留原文，翻译另起一行。
- **判断和事实分开**。你的推断显式标 `[推断]`。
- **局限单独成章**，不要塞在结尾一句带过。厂商自陈的失败模式逐条讲，这是文章价值最高的部分之一。

## 落盘与互链（别省）

**动手前先查 vault 有没有相关文件**，尤其是 cron 类调研可能已经产出过周边仓库的单篇笔记：

```bash
find "$VAULT" -iname "*<关键词>*" | while read f; do printf "%8s  %s\n" "$(wc -c < "$f")" "${f#$VAULT/}"; done
```

如果已有周边单篇，**你的新文档应该做「集中梳理 + 理论补底」并与它们互链**，不要重复建档。

写完必做五件事：

1. **反向互链**：给已有相关笔记追加一行指向新总纲的链接（增量追加，不改原内容）。
2. **wikilink 校验清零**：把文中所有 `[[...]]` 抽出来，逐个检查路径或 basename 能否解析。路径形式写错了要注意——`[[a/b/c]]` 不会 fallback 到 basename 匹配。**校验器必须按 vault 根相对路径测** `os.path.isfile(os.path.join(VAULT, link + '.md'))`；若拿链接当文件名在目录里搜，路径形式的链接会全部误报死链。查全 vault 引用用 vault 真实路径，`grep -r` 不跟随软链。
3. **顺带修既有死链**：校验时如果发现别的文件有死链（常见是漏了 ` 技术调研` 这类后缀），一并修掉。
4. **入口更新**：把新文档加到 vault MOC 对应入口行（增量追加，与该行既有写法保持一致）。
5. **结构复查**：分节写 /tmp 再用 `cat` 拼接时，章节标题前的空行极易丢失，导致标题粘在上一段末尾（渲染错乱）。检查 `(?<=\S)\n## ` 命中数必须归零，是 0 才算拼干净。

## 交付报告

用户在意的三件事：

- **先给结论**：这个东西到底是什么，一句话。
- **给 3–5 个「最值得说的发现」**，每个带具体数字，不是章节复述。
- **列出每个产物的绝对全路径**（硬要求）：新文档、被改动的既有文件、备份位置。

最后问一句要不要沉淀成 skill。

## 踩坑清单

| 坑 | 后果 | 做法 |
|:--|:--|:--|
| 没先确认指代词 | 整篇写错对象 | 先一句话复述确认 |
| 只引官方口径 | 被第三方数据当场打脸 | 三口径必须齐 |
| 把「一致率」当「正确率」 | 结论夸大 | 引用作者自己的限定语 |
| 「0%」直接采信 | 把格式合规当正确率 | 回到原文查它测的是什么 |
| 新概念不追学术源头 | 文章没有理论分量 | 每个术语做一轮学术检索 |
| 忽略厂商自陈的失败模式页 | 丢掉最有价值的一节 | 主动找「已知限制」页 |
| 一次 write_file 写大文档 | 流式超时，白写 | 分节写 /tmp 再拼接 |
| 没查 vault 已有文件 | 重复建档、制造死链 | 动手前 `find -iname` |
| wikilink 只写 basename 或只写路径 | 死链 | 两种都校验 |
| 校验器拿链接当文件名搜 | 路径形式的链接全被误报死链 | 按 vault 根相对路径 `os.path.join(VAULT, l+'.md')` 测 |
| 校验器没剥表格里的转义反斜杠 | Obsidian 表格内写法是 `[[路径\|别名]]`，正则抓到尾部 `\` 导致**整表链接**误报死链 | 取路径时 `.split('|')[0].split('\\')[0]`，并顺手剥尾部 `.md` |
| 对 iCloud vault 跑递归 `find`/`grep -r` | 逼 fileprovider 物化整棵树；更坑的是可能弹出 macOS TCC 授权框，之后**整个 vault 的读全部挂起**（写正常、`stat` 正常、`ls` 目录也挂），表现为“超时”而不是报错 | 查 vault 只用 `os.path.isfile` 逐个试已知路径。需要穷举时先 `~/.local/bin/vfind`，仍不行就放弃穷举，改做定向确认 |
| 长命令 / 多行 shell 循环 | 安全启发式 20 秒无响应即拦（`BLOCKED: Command timed out without user response`），且**同一命令不得重试** | 一律落 `.py`/`.sh` 再一行命令跑；终端调用只写 `python3 <脚本>` 这种短形式 |
| Python 3.14 的 f-string 里放正则反斜杠 | `SyntaxError: f-string expression part cannot include a backslash`——**这条会反复掣者，因为写扫描器时本能地想把 `re.findall` 塞进 f-string** | 先把 `re.findall(...)` 赋给变量，再放进 f-string。写扫描脚本时开头就先把所有统计量算完 |
| 同一项目已有笔记时直接新建 | vault 里可能已有 cron 自动维护的同项目追踪档（`owner__repo 技术调研.md`，带 `trending-log` 与逐日星数），重复建档会造成两个真相 | 先 `ls` 目标分类目录 + `vfind <repo名>`；已有机器追踪档就**另起一份带区分后缀的人工深度调研**，两份互链且各写一句“不重复”，不要合并进 cron 会重写的文件 |
| 用 `grep -r` 查 vault 引用 | 软链根下查不到 | 用 vault 真实路径 |
| `cat` 拼接后标题粘连 | 章节标题挤进上一段，渲染错乱 | 查 `(?<=\S)\n## ` 计数归零 |
| 去 AI 味只跑一遍脚本 | 漏网句式残留 | 通读 + 两轮扫描 + 数口头禅频次 |
| 没列产物绝对路径 | 用户找不到东西 | 报告末尾必列 |
